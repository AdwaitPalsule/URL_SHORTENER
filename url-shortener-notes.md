4. Migration commands to remember
# Generate a migration from model/schema differences
uv run alembic revision --autogenerate -m "describe change"

# Apply all pending migrations
uv run alembic upgrade head

# Show the database's current revision
uv run alembic current

# View migration history
uv run alembic history

# Mark a revision as applied without running its upgrade() function.
# Use only when the existing schema already matches that revision.
uv run alembic stamp head
Important: Autogenerated migrations are drafts. Inspect their
upgrade() and downgrade() functions before applying them. Do not use
stamp head as a substitute for applying real schema changes; stamping
updates Alembic's revision tracking without executing migration
operations.

# Day 2 — Caching & Rate Limiting
**Date:** October 28, 2026

## 1. Today's Goal
Understand caching and rate limiting, why they're needed in backend systems, and how they work in my URL shortener project.

## 2. Caching with Redis

### The problem
When users repeatedly visit the same shortened URL, the application queries PostgreSQL for the original URL on every request.

Even with a database index, PostgreSQL still needs to process those lookups.

### The solution
Use Redis to store frequently accessed URLs so subsequent requests can retrieve them without querying PostgreSQL.

### Cache-aside pattern
1. Check Redis for the requested short code.
2. If the URL exists in Redis, return it — **cache hit**.
3. If it doesn't exist, query PostgreSQL — **cache miss**.
4. Store the retrieved URL in Redis.
5. Redirect the user.

### Implementation in my project
- Redis key: `url:<code>`
- Example key: `url:5`
- Example value: `https://google.com/`
- Cache expiration: 300 seconds (5 minutes)

```python
def get_cached_url(code: str):
    key = f"url:{code}"
    return r.get(key)


def cache_url(code: str, original_url: str):
    key = f"url:{code}"
    r.set(key, original_url, ex=300)
```

### Indexing vs. caching
- **Indexing:** Makes database lookups more efficient.
- **Caching:** Can avoid repeated database lookups by serving previously retrieved data from Redis.

## 3. Cache Invalidation

Cached data can become stale when the original database record changes.

### Updating a link
After updating and committing the PostgreSQL record:

```python
r.delete(f"url:{code}")
```

This removes the old cached URL. The next redirect request fetches the updated URL from PostgreSQL and caches it again.

### Deleting a link
After deleting and committing the PostgreSQL record:

```python
r.delete(f"url:{code}")
```

This prevents the redirect endpoint from continuing to serve the deleted link from Redis.

**Important:** Cache invalidation helps maintain consistency, but failures and concurrent requests can still create temporary inconsistencies.

## 4. Rate Limiting with Redis

### The problem
An endpoint such as `/shorten` could receive an excessive number of requests, consuming application and database resources.

### The solution
Limit how many requests a client can make within a defined time window.

### Implementation in my project
- Limit: 5 requests per IP address.
- Window: 60 seconds.
- Redis key: `rate_limit:<IP>`
- Counter: Incremented using `INCR`.
- Expiration: Set to 60 seconds when the counter is first created.
- HTTP status for excess requests: `429 Too Many Requests`.

### Fixed-window approach
The counter is incremented for each request. When it exceeds five, the application rejects the request.

The expiration resets the counter window automatically.

**Limitation:** A client can make requests near the end of one window and the beginning of the next, potentially exceeding five requests within a short period.
